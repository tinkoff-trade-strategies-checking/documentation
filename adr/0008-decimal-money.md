# ADR-0008: Десятичный тип для денег в C++ и формат в контрактах

- Ответственные: агент `architect`
- Статус: Предложен (предложено агентом, ждёт подтверждения команды)
- Дата: 02.11.2026
- Связано: НФТ-4, INV-4, INV-6, ADR-0007, issue documentation#10
- Оригинал: на Miro нет

## Проблема
Деньги считаются в C++ (портфель, исполнение, издержки), хранятся и показываются через Java. Нужен десятичный тип в C++ без `double` (INV-6), формат передачи сумм в `.proto` и REST и одинаковые правила округления, чтобы результат сходился с ручным расчётом до копейки.

## Факторы
- Точность: цены MOEX бывают с шагом мельче копейки, суммы — до копейки.
- Детерминизм (INV-4): одинаковый результат на любой сборке.
- Простота: четыре студента, без тяжёлых зависимостей.
- Без потерь между C++, Java и браузером.

## Альтернативы
- `boost::multiprecision::cpp_dec_float` — отклонено: число с плавающей точкой, точность задаётся числом значащих цифр, а не знаков после запятой; поведение округления не совпадает с `BigDecimal`.
- Intel Decimal Floating-Point (BID) — отклонено: тяжёлая сторонняя библиотека ради сложения и умножения.
- Строка в `.proto` (`"123.45"`) — отклонено для gRPC: разбор на каждом значении; в REST — выбрано (см. ниже).
- **Свой тип с фиксированной точкой** — выбрано.

## Итоговое решение

**C++.** Класс `Decimal`: целое `absl::int128` (abseil уже приходит с gRPC) — число единиц 10⁻⁹, то есть 9 знаков после запятой.
- Сложение, вычитание, сравнение — точные. Переполнение — исключение, прогон завершается ошибкой.
- Умножение и деление — через промежуточное `int128` с явным режимом округления в каждом вызове; режима по умолчанию нет.
- Конструктора из `double` нет. Перевод в `double` — только явный метод, для метрик и выражений DSL (`dsl.md`).
- Количество бумаг — `int64`, в лотах.

**`.proto`.** Сообщение `Decimal { int64 units = 1; int32 nano = 2; }`, как `google.type.Money` без валюты: значение = units + nano·10⁻⁹, nano в [−999 999 999; 999 999 999], знак nano совпадает со знаком units (или один из них 0). Валюта не передаётся — все суммы в рублях. Применяется для цен, сумм и ставок.

**Java.** `BigDecimal`: `new BigDecimal(units).add(BigDecimal.valueOf(nano, 9))`; обратно — `setScale(9, RoundingMode.UNNECESSARY)`, лишние знаки — исключение (это ошибка, а не повод округлить). Деньги, посчитанные ядром, Java не пересчитывает: хранит и отдаёт. PostgreSQL — `numeric(38, 9)`.

**REST.** Деньги и цены — JSON-строка, шаблон `^-?\d{1,19}(\.\d{1,9})?$`. Числа JSON в JavaScript — `double`, поэтому числом не передаём. Фронтенд только показывает (INV-6).

**Округление.** Правила — в `decisions.md`, раздел «Деньги и округление». Режимы называются как в `java.math.RoundingMode`, в C++ — те же имена.

**Проверка.** Эталонный портфель (INV-6): ~20 сделок с ручным расчётом до копейки — unit-тест в `core`. Тест конвертации `Decimal` ↔ `.proto` ↔ `BigDecimal` на крайних значениях (0, ±10⁻⁹, ±(2⁶³ − 1) units) — в `core` и в `backend`.

## Допущения
- Шаг цены и размер лота каждой бумаги есть в метаданных снапшота (в MOEX ISS — поля `MINSTEP` и `LOTSIZE`; проверить при импорте). Шаг цены не мельче 10⁻⁹.
- Торгуем только рублёвыми инструментами; появится валюта — добавить поле в сообщение.
