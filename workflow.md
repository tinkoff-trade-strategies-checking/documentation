# Как ведём работу

Правила для людей и ИИ-агентов. Цель — чтобы каждая сессия продолжала работу предыдущей, а не начинала её заново.

## Где что живёт

| Что | Где | Не здесь |
|---|---|---|
| Задачи, их статус, ход работы, что отвергли | [доска проекта](https://github.com/orgs/tinkoff-trade-strategies-checking/projects/2) и issue в нужном репозитории | не в локальных файлах и не в памяти агента |
| Что строим | `requirements.md`, `decisions.md` | — |
| Почему так устроено | `adr/` | — |
| Что нельзя ломать | `invariants.md` | — |
| Общее состояние проекта, открытые вопросы | `status.md` | — |
| Как устроен конкретный репозиторий | `AGENTS.md` репозитория | — |

## Доска

[Kanban](https://github.com/orgs/tinkoff-trade-strategies-checking/projects/2) — один на все репозитории; карточка — issue из того репозитория, где будет изменение (общие задачи — в `documentation`).

| Status | Значит |
|---|---|
| Backlog | задача записана, но не уточнена |
| Ready | понятно, что делать и когда готово; можно брать |
| In progress | у задачи есть исполнитель (Assignees) и ветка |
| In review | открыт PR |
| Done | PR влит, issue закрыт |

Size (XS / S / M / L / XL) ставим при переводе в Ready. Задача больше L — разбить на sub-issues.

Агенту для работы с доской нужен доступ `gh` к проектам: `gh auth refresh -h github.com -s read:project,project`. Полезные команды:

```sh
# карточки в работе и готовые к работе — коротко, без полного JSON доски
gh project item-list 2 --owner tinkoff-trade-strategies-checking --limit 200 --format json \
  --jq '.items[] | select(.status=="Ready" or .status=="In progress") | "\(.status) | \(.content.repository)#\(.content.number) | \(.title)"'
# задача и её ход
gh issue view <N> -R tinkoff-trade-strategies-checking/<repo> --comments
```

## Задача от начала до конца

1. **Взять задачу.** Работа идёт только по issue с доски. Нет issue — сначала создать (шаблон «Задача»), указать ФТ и связанные INV, добавить на доску. Перед стартом прочитать issue целиком, включая комментарии: там ход работы и отвергнутые варианты. Назначить себя и перевести в In progress.
2. **Сориентироваться.** Прочитать ФТ, INV и ADR, на которые ссылается задача. Найти в коде похожее решение и переиспользовать его, а не писать параллельное. Если задача требует отойти от ADR — остановиться и предложить новый ADR, а не менять подход молча.
3. **Ветка.** `<номер-issue>-кратко` от `main`, например `42-arena-player`. Прямые коммиты в `main` не делаем.
4. **Сделать.** Небольшими шагами; изменение вместе с тестами. Код, касающийся инварианта, — с тестом, который этот инвариант проверяет.
5. **Если сессия кончилась раньше задачи** — оставить в issue комментарий: что сделано, что осталось, какие варианты попробовали и почему отказались, где остановились (ветка, файл). Следующая сессия начинает с этого комментария.
6. **PR.** В описании `Closes #N`, заполненный чек-лист шаблона. PR от агента ревьюит человек.
7. **Закрыть.** Вместе с кодом обновить документы, которые изменение сделало неверными: `AGENTS.md` репозитория (команды, структура), `status.md`, `decisions.md`; новое архитектурное решение — новым ADR.

## Готово, когда
- тесты и линтеры проходят, CI зелёный;
- инварианты не нарушены, а затронутые покрыты тестами;
- документы соответствуют коду;
- PR одобрен человеком и влит, issue закрыт.

## Чего не делать
- Не переписывать работающий код без задачи на это: рефакторинг — отдельная issue с причиной.
- Не переоткрывать решённое: принятый ADR и закрытый вопрос из `status.md` меняются только новым ADR.
- Не дублировать знания: правило живёт в одном месте, остальные ссылаются на него по ID.
- Не держать важное только в чате, локальных заметках или памяти агента: следующая сессия и коллеги этого не увидят.
